Paper and presentation

This transcript follows the approved recording, which uses synthetic narration approved by Mick. It covers the main presentation only. Timestamps are navigation labels; unspoken slide titles and the 24 backup/Q&A slides are not part of the narration.

The published paper remains the source of truth for its peer-reviewed claims. The full deck labels additional research as “Beyond the paper. Not peer reviewed. Review welcome.”

00:00

A quarter century ago, British Telecom reported nine nines of service availability in one of its telephone switching systems. That’s equivalent to about 30 milliseconds of downtime a year. They achieved that with components engineers knew would fail built with Erlang and its open telecom platform OTP. The system used redundancy and recovery to contain those component failures and keep service running. That’s the question behind this paper. Can OTP help AI systems succeed reliably despite component failures?

Today’s agents can crash loop, drift off task, or hallucinate. With tool access, they can make inappropriate or dangerous tool calls, read API keys and private data outside their authorized task, or exfiltrate data. Security evaluations repeatedly demonstrate tool misuse and data leakage, including successful attacks against systems with defenses. We want whole systems that coordinate many workers, enforce what each can read and do and keep useful work moving when individual agents break in any of these ways or in ways we haven’t anticipated.

On our test tasks, OTP-style supervised configurations delivered substantial gains in reliable task completion with the same language model. In two selected internal comparisons, frontier model configurations incurred roughly 4 to 20 times as much in language model charges per successfully completed task run as smaller model configurations. That calculation includes failed attempts and recovery. Success rates differed, so these observations do not establish savings at equal quality or cover the full cost of operating the system.

Our mapping shows which patterns transfer and where the engineering must change. It points to the work ahead, extending those capability gains and building toward telecom-style availability. I’m Mick Darling, founder of Dollhouse Research, an AI lab. We build platform agnostic tools that make AI more capable and give people the visibility and control to govern its behavior. I’m the lead inventor on four natural language processing patents. That work began in the early 2010s using Erlang OTP workers to analyze the meaning of unstructured social media text in real time.

We processed millions of messages for live television, including American Idol. That experience helped us recognize familiar engineering problems in multi-agent systems. I also want to thank the chairs, reviewers, and proceedings team for helping bring this paper to publication and for their patience with me along the way. They’ve inspired a new agentic benchmark navigating the publication process without asking the chairs for help. I can report that the human baseline required considerable assistance.

An agent that could do it unaided would be a remarkable uplift in at least this human’s capability. The immediate problem in our production system was waiting.

02:45

It arose in DollhouseMCP, an MCP server we use for agent management. In the setup I’m describing, it runs locally. There are four distinct parts here. The model generates responses. The harness is the application that calls the model and coordinates tool use. MCP, the model context protocol, lets that application access tools exposed by a server. Our agent is the managed unit of work with an identity, state, and a mailbox for messages. Its lifetime can span several model calls.

Some agents needed to wait hours for an outside event. One unattended component repeatedly called on the model to check for updates and consumed most of a weekly quota. An open idle session doesn’t inherently consume tokens. Those repeated inference calls do. We moved responsibility for waiting into the server. Ordinary code retains the agent’s identity and messages without keeping a model call active or awaiting its completion. We call that parking.

It uses computing resources but no inference tokens while parked. An event, timer, or server side result can mark the agent as ready to continue. A client or dispatcher must then arrange the next model call. How that happens depends on the deployment. Retaining state does not by itself provide the whole wake up mechanism. A harness can also wait for events without repeatedly calling the model. We put lifecycle state in the server to separate the agent’s lifetime from individual model interactions.

Routing tool requests through that server also gives us a place to apply access controls before those tools execute.

04:25

Once ordinary code controls when an agent starts, waits, and stops, it can also monitor work, start a fresh model call after a failure, and limit how often that happens. That’s supervision. In OTP, processes have identities and mailboxes. Supervisors watch workers and apply recovery rules after a failure. In April 2026, we recorded how these OTP constructs corresponded to our runtime in dated engineering issues. We deliberately applied the patterns, then ran the planned experiments in July.

05:00

Could OTP help us predict failures and useful fixes in agent systems? We first mapped 20 OTP constructs to their proposed agent counterparts, judging how faithfully the behavior transfers. We then ran pre-registered experiments, comparisons, and analysis rules set before running the models. Those compared supervised configurations with simpler loops across model tiers. Finally, we examined the differences that prevent a faithful mapping. Production experience motivated the investigation.

The mapping and experiments test different claims, and neither requires agent frameworks to be implemented in Erlang.

05:36

Of the 20 OTP constructs, twelve had exact operational mappings their proposed agent counterparts preserve all the operational behavior relevant to the comparison. Five mapped more loosely, the general function carries over, but documented differences prevent a fully faithful mapping. For three, the mapping breaks because the agent infrastructure we examined offers no faithful counterpart. Those grades describe behavior, not just resemblance in names.

Take parking, one of the exact mappings. An Erlang process waiting for a message retains its identity and mailbox without doing work. Our parked agent also retains an addressable identity and mailbox without keeping a model call open. The resources differ, but both separate the worker’s continuing existence from its current activity. Calling that mapping exact does not certify every implementation or give an agent every guarantee of an Erlang process.

We assign the grades ourselves, and they have not been independently audited. The dated record and evidence for each row let others inspect and challenge those judgments.

06:39

Two of the examples in this table show how the mapping guided repairs. A supervisor also needs a limit on restarts, otherwise it can keep restarting a failing worker indefinitely. After that limit, it needs to escalate the failure rather than retry forever. Workers also need a defined relationship to their client session. Some of ours kept running for days after their sessions died. Linking those lifetimes gives the system a rule for stopping work when its owning session ends.

These were fixes for DollhouseMCP. We recorded the designs in April before the matching incidents appeared. As the paper notes, our runtime’s designers already knew Erlang. This record shows us applying prior knowledge. It motivates the mapping without independently auditing it.

07:25

The three constructs without faithful counterparts show where the underlying infrastructure matters. First, Erlang processes are isolated from one another by default. LLM systems often accumulate observations and contexts, and some share a growing history. We can give workers fresh context as an isolation policy that does not provide the same built-in guarantee as separate Erlang process memory. Second, an Erlang process checks structured message values against expected patterns.

A model interprets the content it receives, including prose inside an otherwise valid message. That prose can contain an instruction or an injection attack. Checking the message’s structure does not establish that its meaning is safe. Third, Erlang can interrupt a process during execution and let other processes run. The hosted model interfaces available to us did not expose comparable control inside an inference call. We could monitor calls, impose timeouts, and control what happened between calls.

That is a limit of the interfaces we evaluated, not a claim that model inference can never become interruptible. These are substantive differences. Organizing agents into a supervision tree does not automatically give them all of Erlang’s guarantees. To test a configuration, we built a standalone research harness separate from the production MCP deployment.

08:34

It assigns work to LLM workers and checks their messages and outputs. The supervisor responds to reported failures. A separate experimental grader scores answer correctness. Supervisors, routers, validators, and mailboxes are ordinary code. One worker activation is one model call. After a failure, a replacement receives its assigned work in a fresh context without the failed call’s accumulated history. Task state is retained outside that context. The persistent production agent we parked earlier is distinct from these individual model calls.

When we report actor count, we mean the configured LLM workers excluding control code and additional calls made for recovery. The supervisor can detect crashes, timeouts, invalid message structure, and outputs that fail the configured requirements. It can replace a failed activation, hold a suspect message aside, or escalate after the restart limit. A confident wrong answer that passes those checks may produce no failure signal. The first study compares three configurations.

A is the supervised system. B is a simpler loop with a fixed retry policy that retains prior context. C makes no retries. A later comparison adds S, a control that generates multiple candidate answers. A combines several design choices so these comparisons cannot identify fresh context alone as the cause of improvement. Workers run sequentially. The experiments establish no concurrency latency or throughput advantage.

10:13

We tested eight model tiers from models with 1.7 billion parameters to frontier models. The first study uses multistep tasks in the style of the GAIA benchmark. We check whether each final answer exactly matches the expected answer after applying predefined rules for how answers are written. A plausible intermediate step does not count as success. Each task gets four complete runs under each configuration. A run may include its permitted retries, but those retries do not count as additional runs.

Our reliability metric, pass to the fourth, counts a task as successful only if all four runs produce correct final answers. We analyze those task level results rather than treating retries as independent observations. The later scaling study uses harder problems that can be divided into components. Workers follow chains of proof, trace where information came from, compare possible fault causes, or allocate resources under constraints. These represent aspects of software engineering work rather than an end-to-end coding benchmark.

We set acceptance conditions for each conclusion before running the models. When a condition failed, we withheld that conclusion, even if other measurements remained usable.

11:26

Each result here reports the proportion of 20 capability tasks that succeeded on all four complete runs. With Ministral-3B, the supervised configuration reaches 95%. Both the retry loop and the no-retry loop reach 65%. With Qwen3-32B, the supervised configuration reaches 70% compared with 45% for the retry loop and 5% without retries. Retries alone clearly help. Supervision adds 25 percentage points beyond that retry control. That improvement belongs to the whole supervised configuration.

We did not separately test how much comes from fresh context. Across the five tiers where results distinguish the configurations, supervision leads both controls at four and ties the stronger control at one. The frontier models reach 100% under every configuration while the smallest model reaches zero. Those results cannot show an improvement on this task suite. With only 20 tasks per result, this is a pilot study. We make no statistical significance claim for an individual result.

These models also differ in more than parameter count. So our defensible comparisons use the same model under different configurations.

12:38

Could the improvement simply come from generating more attempts? We tested a best-of-N control that runs the simpler unsupervised loop to generate candidate answers then selects one. The selector checks the required format and uses agreement when several candidates fit the budget otherwise it takes the first valid answer. It cannot see correct answers or grading results. We compared configurations on the same 20 tasks initially across three model tiers then with fresh runs at 32B the initial comparison averages across tiers.

Success means a correct individual run rather than requiring all four runs of a task to succeed. Supervision’s advantages are about 33 percentage points in the initial study and 26 in the replication with p-values at or below 0.004. Across 320 sampling control task runs, the selector never turned a failed first candidate into a successful selected answer. This concerns the tested selector and sampling schedule. It does not rule out stronger sampling methods or identify which feature of supervision caused the advantage.

Both studies aim to keep sampling token spending within 10% of supervision spending. Both miss that band in opposite directions. We therefore have evidence of an advantage but cannot claim it was established with matched computational resources. A stronger comparison must enforce the budget without using outcomes to decide how much to spend.

14:08

Can dividing work among supervised workers help on harder problems? Here the apparatus supplies 16 component problems and a plan for assigning them. With one worker a single model call answers the whole batch with 16 workers each answers one component. Ordinary code assembles the results and workers run sequentially. We test execution of the supplied plan rather than asking models to invent the decomposition. We now measure component accuracy the proportion of components answered correctly.

Missing or incomplete output counts as failure. That is different from requiring an entire task to succeed. The control code stays fixed as worker count changes. On tasks reserved in advance for evaluation, Qwen3-32B rises from 57.4% with one worker to 81.6% with 16. That’s a gain of 24.2 percentage points with a 95% confidence interval from 13.3 to 35.5. Repeating the experiment in a separately provisioned setup yields 53.5% and 80.9%. Haiku 4.5 instead peaks at four workers, at 54.7%, then falls to 34.0% with 16.

Worker count therefore needs to suit the model and task. In the paper a controller that adjusts worker count during execution is proposed future work. The paper does not report a test of one. That Qwen reproduction failed the requirements for matched resource spending. We can report its accuracy but not matched cost savings. We separately exclude Sonnet 5’s apparent gains. Dividing its batch repairs a JSON output format problem rather than demonstrating better reasoning.

15:53

This leaves research questions beyond the three constructs that failed to map. First, how do we recognize an answer that is wrong in meaning? A worker can return a confident well-formed answer that passes validation. The supervisor then sees no reason to restart it. Recovery needs an observable failure signal. Second, fresh contexts limit what each worker receives, but they are only part of our isolation policy. A message permitted through an allowed path can still carry instructions that influence subsequent work.

Fresh context alone does not make those messages trustworthy. Third, recovery has a cost. Each fresh model call consumes tokens, time, and money. Restarting is not automatically worth the expense. In the paper we did not establish the matched cost claims. OTP supplies useful defaults but applying them still requires understanding the model and failures we can detect.

16:50

There are two judgments here. How faithfully an OTP pattern maps to an agent system and how much evidence we have for its implementation. An exact mapping describes the operational correspondence. It does not certify a complete implementation or tell us how much one mechanism contributed to the measured gain. The paper separates implementation evidence into three levels. Tested means sealed preregistered evidence including the integrated supervision and decomposition studies we’ve just seen.

Spot means validation or exploratory evidence. For example, the deterministic injected fault test produced all 18 expected outcomes. That checks those recovery cases but does not establish a comparative capability gain under injected faults. Gap means a design with no experimental result in the paper. Continuous feedback control and heterogeneous fleets are examples. Keeping these evidence levels separate lets us distinguish a useful architectural correspondence from a result we have actually measured.

17:49

The paper proposes three next tests. These are research questions not completed confirmatory results. First, compare supervision with the retry loop on a paid grid of deliberately injected faults. Does adding those faults widen the supervision advantage? The deterministic self-tests on the previous slide do not answer that comparative question. Second, test whether a supervised small model configuration can match a clearly defined frontier baseline on the same suite and measure the corresponding cost ratio.

The pilot’s cross model observations motivate that question but do not establish parity at equal quality. Third, sweep actor counts across models and task families. Can we predict which level of decomposition suits a given model and task, instead of assuming that more workers always help? Each conclusion must meet its pre-registered acceptance conditions. The paper’s proposed tests remain distinct from the separately labeled research updates in the backup slides.

18:50

The unit we measured is the configured system, the model together with supervision validators and retained task state. On the pilot tasks, Ministral-3B reached 95 percent reliable task completion with supervision compared with 65 percent without retries. Reliable here means that a task passed all four complete runs. On the harder decomposable tasks, Qwen3-32B’s component accuracy rose from 57.4 percent with one worker to 81.6 percent with 16 using the plan supplied by the apparatus.

Haiku instead peaked at four workers and fell to 34.0 percent at 16. Worker count must suit the model and the task. These results show why we need to evaluate the system managing a model’s work as well as the model itself. The paper DOI is on the slide.

Thank you. I’m happy to take questions.
